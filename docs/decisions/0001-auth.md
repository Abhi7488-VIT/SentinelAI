# ADR 0001 — Authentication: short-lived JWT access token + rotating refresh token

- Status: **Accepted** (2026-11-17, with Phase 1 plan approval)
- Date: 2026-11-17
- Phase: 1 (Foundation)

## Context

SentinelAI needs authentication for:
- the first-party Next.js web UI (browser),
- later, non-browser clients: CLI, CI jobs, testbed/evaluation scripts, and SSE progress streams (Phase 4),
- multi-tenant authorization where a user's role can differ per organization and can change at any time.

Constraints from `CLAUDE.md`: tenant isolation enforced in one place, secrets only via env, nothing secret in logs, honest about trade-offs.

## Options considered

### A. Server-side sessions (opaque session ID in an httpOnly cookie, session row in Postgres/Redis)
- \+ Simplest model; instant revocation; no token crypto.
- − Cookie auth on every mutating endpoint requires CSRF protection on all of them.
- − Non-browser clients would need a second mechanism anyway (API keys / bearer tokens).
- − Every request needs a session-store lookup (acceptable, but we gain nothing over B on this axis).

### B. Short-lived JWT access token (Bearer) + opaque rotating refresh token in an httpOnly cookie  ← **chosen**
- \+ One auth mechanism (`Authorization: Bearer`) for browser and non-browser clients.
- \+ Bearer header is not sent automatically by the browser → mutating endpoints are not CSRF-exposed. Only `/auth/refresh` and `/auth/logout` read a cookie; they are protected by `SameSite=Strict`, `Path=/api/v1/auth`, and an `Origin` allow-list check.
- \+ Refresh tokens are server-side state: revocable (logout), rotated on every use, and **reuse detection** revokes the whole login family if a rotated token is presented again (signals theft).
- − More moving parts than sessions.
- − An access token cannot be revoked before expiry (≤ 15 min window after logout/compromise).

### C. Long-lived JWT only (no refresh)
- Rejected: no revocation, long exposure window.

## Decision

Option B, with these specifics:

| Aspect | Decision |
|---|---|
| Access token | JWT, **HS256**, 15 min TTL. Claims: `sub` (user id), `iat`, `exp`, `jti`, `iss`, `aud`, `typ="access"`. Verification pins `algorithms=["HS256"]` and requires `exp/iss/aud`. Secret `JWT_SECRET` from env, ≥ 32 bytes, validated at startup. |
| Roles in token | **No.** Org membership/role and `users.is_active` are loaded per request, so role changes and deactivation apply immediately. This costs one indexed PK lookup per org-scoped request, which we need for tenant gating anyway. |
| Browser storage | Access token in **memory only** (never localStorage). On page load the app calls `/auth/refresh` to obtain one. |
| Refresh token | 256-bit random, base64url; only its **SHA-256 hash** is stored (`refresh_tokens.token_hash`, unique). 14-day TTL per token, 30-day absolute cap per family. Rotated on every refresh; old token marked used and linked via `replaced_by_id`. |
| Reuse detection | Presenting a used or revoked token → revoke every token in the family, audit `auth.refresh.reuse_detected`, 401. A short grace for concurrent refreshes is **not** implemented; the frontend single-flights refresh to avoid self-inflicted reuse. |
| Cookie | `sentinel_refresh`; `HttpOnly`; `SameSite=Strict`; `Path=/api/v1/auth`; `Secure` controlled by `COOKIE_SECURE` (must be true when `ENV=prod`). |
| Password hashing | argon2id (`argon2-cffi` defaults per RFC 9106), executed in a worker thread to keep the event loop free; rehash on login when parameters change. Password length 12–128. |
| Login hardening | Same error (`invalid_credentials`) and comparable timing for unknown email vs wrong password (verify against a dummy hash). Redis rate limits per IP and per email on register/login/refresh; limiter fails **closed** (503) if Redis is unavailable. |
| Audit | Login success/failure, refresh, reuse detection, logout, registration recorded in `audit_logs` with request id, IP, user agent — never passwords or tokens. |

## Consequences

- Machine clients (Phase 3+ OTLP ingestion, CI) will use separate, scoped **API keys** (`api_keys` table), not user JWTs. That will get its own ADR.
- SSE in Phase 4 cannot use native `EventSource` with a Bearer header; the client will use `fetch` streaming (which also lets us send `Last-Event-ID` explicitly).
- If the ≤ 15 min post-logout window becomes unacceptable, add a `sid` (family id) claim and check family revocation per request — a cheap indexed lookup — without changing the client contract.
- Moving to asymmetric signing (EdDSA/RS256) is only needed if another service must verify tokens; not planned (modular monolith).
